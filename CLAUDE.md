# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An R codebase for simulating cane toad (*Rhinella marina*) spread across waterpoints in north-western Australia. It supports Dunlop *et al.* (submitted 2025), which extends the point-process spread model of Tingley *et al.* (2013, *J. Appl. Ecol* 50:129-137) to:

1. Estimate arrival time of toads in the Pilbara / at the Toad Containment Zone (TCZ) under a do-nothing scenario.
2. Optimise investment in the TCZ (fencing/converting artificial waterpoints, accounting for natural waterpoint drying probability) to test containment scenarios.

This is a research script repository, not a package — there is no `DESCRIPTION`/`renv.lock`, no test suite, and no build/lint tooling. Everything runs interactively from RStudio (`TCZ-sims.Rproj`) or via `Rscript`, and scripts are meant to be `source()`d in a specific order (see below), populating the global environment as they go.

## Running things

There is no build, lint, or test command. To run a simulation:

```r
# from repo root, in an R session
source("src/tcz-sims/tcz-sims.R")      # full TCZ implementation scenario
source("src/tcz-sims/tcz-optimise.R")  # greedy design optimisation (set SMOKE <- TRUE first for a ~1 min plumbing check)
source("src/tcz-sims/forecast.R")      # do-nothing forecast from current invasion front
```

All of these `source("src/tcz-sims/load-data.R")` internally, which pulls in raw spatial data. **`load-data.R` requires the `DATA_PATH` environment variable** to be set to a local directory containing the Fulcrum infrastructure audit export, GIS layers, and invasion-front parameters (`Toads/TCZ/infrastructure/...`, `GIS - General/GIS_layers_read_only/...`, `invasion-front-parameters.Rdata`) — none of this lives in the repo. The TCZ scenarios also need network access the first time (SILO via `SILO_API_KEY` in `rain-years.R`, DEA Waterbodies in `drying-model.R`); both cache what they fetch in `dat/` (`silo-tcz-rain-cache.RData`, `dea-drying-cache.RData`), so later runs work offline.

For the HPC (cluster) workflow, `src/cluster/a-setup-environment.sh` loads the required environment modules (`r/4.3.0`, `gdal`, `geos`, `proj`, `udunits`) before invoking scripts with `commandArgs`.

The public forecast site is a separate deployable unit in `shiny/`. Run `shiny/prep_app_data.R` after a `forecast.R` run: it does all the spatial work (`sf`, Albers reprojection, per-year colonisation probabilities) and writes `shiny/data/app_data.rds`, then sources `shiny/export_web_data.R`, which converts that `.rds` into static files in `shiny/web/data/` (`forecast.json`, `tcz.geojson`, `pastoral.geojson`). The export drops waterpoints inside the TCZ polygon from the public map (they stay in the simulation and the `.rds`). **The live site is `shiny/web/`**: plain HTML + Leaflet (`index.html`, `app.js`, `style.css`), no R in the browser and no build step. Branding follows the `data-warehousing` reporting apps (accent-only Rock/Sand `--tcz-*` tokens in `style.css`; `tcz-mark.svg` and favicons copied from `data-warehousing/app/toad-reporting/www/`); the YlOrRd data colours stay as they are. `.github/workflows/deploy-shiny-pages.yml` publishes that folder to GitHub Pages on any push to `main` touching `shiny/web/**`, so commit the regenerated `shiny/web/data/*` to update the site. The site is served at **`https://forecast.toadfree.zone/`** (custom domain set 2026-11-26, HTTPS enforced; `toad-containment-zone.github.io/TCZ-sims/` 301-redirects to it). The domain is configured in the repo's Pages settings, not by a `CNAME` file, because Actions-built Pages ignore one. DNS is a GoDaddy CNAME `forecast` → `toad-containment-zone.github.io`, plus the org-level domain-verification TXT record; both are managed by a colleague, not the project lead. All asset paths in `index.html` must stay relative. It replaced a shinylive build (2026-11) whose first load fetched ~70 MB of webR runtime and wasm packages (mostly `sf`/`terra` pulled in by `leaflet`'s Imports); the web data is ~210 KB gzipped. Preview locally with `python3 -m http.server -d shiny/web`; `window.tczForecast` in the browser console exposes the map, markers and `setYear(i)` for debugging. The original Shiny app (`shiny/app.R`) and its shinylive build script were deleted once the JS site was live; they're in git history if ever needed. `prep_app_data.R` runs both inside a `forecast.R` session (boundary sf objects already in scope) and standalone (it then reads `tcz.boundary` from `DATA_PATH` and `pastoral.boundaries` from `out/pastoral-boundaries.shp`); `export_web_data.R` can also run on its own from the repo root, needing only the `.rds`.

Manuscript output (`ms/tcz-optimisation-methods.qmd`) renders via Quarto (`_quarto.yml` sets `output-dir: ms/output`); it references figures written to `out/` by the simulation scripts, so simulations must be run before rendering.

## Architecture

### Core simulation engine: `src/pprocess_functions.R`

Every scenario script sources this file. It is the single workhorse module with no other internal dependencies within `src/`:

- **`setup()`** — builds the `spread.table` (matrix of waterpoint ID/X/Y/target/kernel-params/presence/age/natural-flag) and the sparse pairwise dispersal matrix (`pairs`), from a point dataset, kernel parameters (`dat/Kernel-fits_truncated.RData`), and posterior draws (`dat/Posteriors*.RData`). Both outputs are placed directly into the global environment via `list2env`. Thins points to non-overlapping detection discs (`thin_overlapping()`: radius `max(r, r.eff)`, survivors chosen units > colonised > observed > targets > rest; units and `keep.id` points always kept, which `tcz-setup.R` uses for natural water inside the TCZ; `threshold=` is retired and errors) and optional TCZ-area filtering. Also unconditionally adds `occ.years`/`first.col.gen` bookkeeping columns, and (only when the corresponding optional arguments are supplied) `control.type`/`r.eff`/`fence.units`/`p.breach`/`surv.prob`/`control.fail.prob` columns that drive the optional control step in `spread.pilb()` — see below. All of these default to no-op values (`CONTROL_NONE`, `NA` `r.eff`, `surv.prob=1`, etc.) when the relevant `setup()` argument is omitted, so every scenario script that doesn't pass them is unaffected.
- **`spread.pilb()`** — advances the population one generation at a time: draws Poisson propagule counts from occupied sites, spreads them through the dispersal kernel matrix, draws realised colonisation via a multinomial (a point is colonised when at least `COLONISE_MIN` = 2 colonists arrive), and stops early once any/all target site(s) are colonised. Optional args (all default off): `control.step=TRUE` turns on a within-timestep "control step" after colonisation each generation — natural points survive via `surv.prob` (a static 1 = never dries, until a real drying model is wired in), tank/fence points are re-tested every generation they're occupied via `control.fail.prob` (`1-control.fail.prob` = extinction probability; defaults 0.01 tank / 0.05 fence per `ms/tcz-optimisation-methods.qmd`), and fenced points additionally get their arrival counts thinned by `p.breach` (from fence length + gates) at the colonisation step, using an inflated per-point detection radius `max(r, r.eff)` in place of the global `r` (`R_DETECT` = 300 m, the one value `run_sims()` and `eval_design()` both use; λ is calibrated given it). `stop.on.target=FALSE` disables the early-exit-on-breach behavior (needed for full-horizon point-years accounting). `rollup=TRUE` and `control.step=TRUE` together raise an error — rollup's propagule-emission shortcut is irrelevant at TCZ scale (a few hundred points) and would silently hide extinction-eligible sites from testing. See `src/tcz-sims/control-step-demo.R` for a synthetic worked example of all of this against made-up tank/fence/natural point data.
- **`run_sims()`** — repeatedly calls `spread.pilb()` (default 100 reps), resampling `lambda` from a log-normal posterior each rep. Passes through `control.step`/`stop.on.target`/`drying.matrix` to `spread.pilb()`. With `extreme.ref` (one flag per reference year) and `pairs.extreme`, each rep starts at a random reference year and wraps round it (`year_index()`), using the extreme-wet-year kernel in the flagged generations; the start is stored in each rep's output. `extreme.years=` instead gives a fixed per-generation sequence with no random start (the Kimberley ABC's real 2010–2023 history).
- **Extreme-wet-year kernel and eradication counting** — `setup(rain.extreme.id=)` builds a second dispersal matrix `pairs.extreme` from each point's extreme-year rainy days (the kernel table covers 1–365 movement days, so nothing is capped; `setup()` stops if a lookup exceeds it), and `spread.pilb(pairs.extreme=, extreme.years=)` uses it in extreme generations. `setup()` always adds an `erad.events` column, which the control step increments for every occupied fence (one eradication response per audit that finds toads).
- **`save_outputs()`** — writes `.RData`/`.csv` summaries (mean arrival year per point, per-year colonisation-probability tables for animation) to `out/`. `extinction.aware=TRUE` switches the arrival-year calculation from `age`-based inference (which assumes permanent occupation) to the direct `first.col.gen` record, needed once `control.step` extinction/recolonisation is in play.
- **`make_plots()`** — builds static (`tmap`) arrival-year maps and an animated GIF (`magick`) from the dynamic-map CSVs; cleans up intermediate frame files afterward.
- Dispersal kernel: `dcncross()` / `dcncross.trunc()` implement a truncated Cauchy-normal (2D t-like) kernel; `rain_to_days()` converts rainy days to days of toad movement: a rough saturating guess (about 4 days per rainy day early on), levelling off at `season.days` (default 212, the Nov–May movable season; `setup(season.days=)` passes it through, and `forecast.R` pins 365 until it moves to SILO). The kernel table (`dat/Kernel-fits_truncated.RData`) is fitted for 1–365 movement days.

Every scenario script follows the same shape: source dependencies → load point data → call `setup(...)` with dataset-specific column names → `run_sims()` → `save_outputs()` → `make_plots()`.

### Scenario/data pipeline: `src/tcz-sims/`

This is the current, actively-developed pipeline (superseding the scripts now in `src/archive/` — see below).

- **`load-data.R`** — the shared data-assembly step. Reads the Fulcrum TCZ infrastructure audit (geojson), joins per-site costs on `ParentID` = `X_record_id` (from `optimisation-data/Activity Steps Toad project - 4 crew - 9Jul26.xlsx`, sheet "Analysis"; `Cost/Site` is the direct infrastructure cost only, project totals are kept in `cost.totals`) and fence lengths/gates, reads eradication costing from the same fencing workbook (`erad.units` per fence on `fence-lengths`, × the $/erad-unit night on `eradication-costs-per-erad-unit`; one response = one night), loads legacy LaGrange points and the Living Waters natural points (`DATA_PATH/Toads/TCZ/living-waters/living_waters_points.geojson`, carrying the drying survey's `group_assessment`), extracts rainfall raster values, calls `score_colonised_multi_year()` to flag colonised points, reprojects to Albers (EPSG:3577), and produces the diagnostic figures `out/time-to-tcz.png` / `out/tcz-waterpoints.pdf`. It builds **two point sets**: `all.points` (every audit record as its own point; used by `forecast.R`) and `tcz.points` (audit records replaced by intervention units; used by `tcz-sims.R`).
- **`build-tcz-units.R`** — `build_tcz_units()`: turns audit records into intervention units, one simulated point each, so the optimiser can remove one intervention at a time. Records in a fenced enclosure (the `fence.enclosures` table, keyed by `X_record_id`) become one fenced unit; remaining records within 100 m are merged (otherwise `setup()`'s de-duplication silently drops them and their costs). Unit cost is the members' summed `Cost/Site`; `candidate = cost > 0` ("Nothing"-status and uncosted units are fixed controlled points). Writes `out/tcz-units.csv` via `load-data.R`.
- **`get-invasion-front.R`** — `score_colonised()`: reconstructs the current invasion-front line (fit elsewhere, stored in `invasion-front-parameters.Rdata`) in Albers coordinates, and classifies each point as colonised/not based on position relative to that line and to fixed geographic anchor points (Fitzroy River mouth, a southern boundary point).
- **`rain-years.R`** — `rain_years()`: daily SILO rainfall per 0.05° cell under the simulated points (cached in `dat/silo-tcz-rain-cache.RData`, or another file via `rain_years(cache=)`, saved every 100 fetched cells so a long fetch resumes; needs `SILO_API_KEY` for uncached cells), summarised per season year (Jul–Jun) as Nov–May rainy days (≥1 mm) and wet-season (Dec–May) mm. Gives the 25-year reference (`rain.years$ref`, 2002–2026) with the top 20% by regional wet-season mm flagged `extreme`, each point's maximum rainy days (sets the extreme kernel), and the per-cell-year table (plus 2000–01 for lags) for the step 5 drying matrix.
- **`tcz-setup.R`** — shared setup for the TCZ scenarios: buffers the TCZ boundary by 80km, defines north-of-TCZ as already colonised and south-of-TCZ as target points, and runs `setup()` on `tcz.points` with `TCZ = FALSE`, so TCZ intervention units stay in the run as tanks/fences handled by the control step (not removed). It then checks that every unit survived de-duplication, and builds `tcz.units.sim` (unit ID, cost, candidate per `spread.table` row). It also sources `rain-years.R` and takes **both kernels from SILO**: `rain.id = "rain.mean"` (each point's mean rainy days over the reference years, replacing the raster `rainfall` that `forecast.R` still uses) and `rain.extreme.id = "rain.extreme"` (the maximum), so `setup()` builds `pairs` and `pairs.extreme` from one source.
- **`tcz-sims.R`** — the "what if the TCZ is fully implemented" scenario: sources `tcz-setup.R`, then `run_sims(control.step = TRUE, stop.on.target = FALSE)` → `save_outputs()` → `make_plots()` (`out/tcz-full.*`).
- **`optimise-functions.R`** — `apply_design()` (remove interventions from a copy of `spread.table`: the water stays, uncontrolled; a removed fence keeps its effective radius `r.eff` and loses only its breach thinning and control test), `eval_design()` (n runs of one design in parallel via `mclapply`, with common random numbers: run r always uses `set.seed(seed + r)`), `design_cost()` (capital + recurrent + eradication), and `greedy_backward()` (single pass, most expensive first; then a confirmation on a separate seed block that, while it finds breaches, restores one unit: `restore = "best"` (default) replays the breaching runs with each still-removed unit restored and puts back the one fixing most breaches per capital dollar; `"reverse"` is the steps 3–5 rule). `eval_design(runs=)` replays chosen run numbers; `eval_design(erad.cost.row=)` costs each run's eradication responses per fence.
- **`tcz-optimise.R`** — runs the do-nothing counterfactual, the full design, the greedy search and the optimised design, at 100-run screens, a 1,000-run confirmation and 1,000-run evaluations ("0 in 1,000" bounds breach risk at ~0.3%; the full run takes tens of minutes on 8 cores), and writes `out/optimisation/` (`greedy-log.csv`, `restorations.csv`, `design.csv`, `summary.csv` with breach probability, point-years avoided, cost and CE, and `optimisation.RData`).
- **`forecast.R`** — the "do nothing" scenario from the real current invasion front (`TCZ = FALSE`); this is the one that feeds the public forecast site (`source("shiny/prep_app_data.R")` at the end).
- **`drying-model.R`** — natural-point drying (supersedes `dea-drying-probs.R` and `rainfall-drying-model.R`, kept for reference but not sourced). Traditional Owner assessment decides *whether* a point dries; DEA only *how* drying responds to rainfall (DEA shows the "Always Wet" points reaching 0% open water in most dry seasons, so it can't calibrate whether). `dea_drying()` matches Living Waters points to DEA Waterbodies within 100 m and scores Jun–Dec dry seasons (cached in `dat/dea-drying-cache.RData`); `fit_drying_response()` fits `glmer(dry ~ wet_sc + lag_sc + (1|site))` with SILO wet-season rainfall from `rain-years.R`; `drying_spec()` classes each `spread.table` row as never/sometimes (Living Waters "Always Wet" → never; other Living Waters → sometimes; all other natural points → never) with per-year rainfall anomalies; `draw_drying_matrix()` gives a run's drying probabilities, logit p = logit(0.25) + b1·x1 + b2·x2. `run_sims(drying.spec=)` / `eval_design(drying.spec=)` draw (b1, b2) per run and use the run's random start, so drying and the extreme kernel follow the same year sequence.
- **`control-step-demo.R`** — self-contained synthetic demo/regression script (no `DATA_PATH` dependency) for the control-step mechanics in `pprocess_functions.R` (see above): builds made-up tank/fence/natural point data, checks that `control.step=FALSE` reproduces legacy permanent-occupation behavior, checks tank/fence extinction rates and fence breach-thinning behave as designed, and sanity-checks the `occ.years`/`first.col.gen` bookkeeping columns. Real per-site `control.type`/`fence.area`/`fence.units` data is now wired through `load-data.R`/`tcz-sims.R`; see `docs/roadmap.md` for what's still outstanding.

Data flow through this pipeline: `load-data.R` → (`tcz-sims.R` | `forecast.R`) → `save_outputs()`/`make_plots()` → (for forecast only) `shiny/prep_app_data.R` → `shiny/export_web_data.R` → `shiny/web/`. Natural-point drying (`drying-model.R`) is wired in through `tcz-setup.R` (`drying.spec`) — read `docs/roadmap.md` (the roadmap to finalise this work: phases, standing decisions, open questions; the optimisation steps 1–6 record is archived in `docs/archive/optimisation-plan-2026-11.md`) before extending this further.

### Legacy/adjacent folders

- **`src/archive/`** — model applications that are no longer maintained (`tingley-sims/`, `pilbara-impact-sims/` (Dunlop *et al.* submitted 2025, Methods 2 and 3), `paruku-impact-sims/`, and the original VRD ABC scripts). They predate c ≥ 2, `season.days = 212` and the SILO kernels, so running them against the current engine mixes old and new; `src/archive/README.md` says how to reproduce them (commit `b6432e9`).
- **`src/null-model/predict-front-displacement.R`** — runs the model one generation forward from each year's fitted front and compares the simulated displacement with the observed one (from `invasion-front-monitoring`). Live, on the shared calibration, but frozen at `season.days = 365` with raster/all-year rainy days until Phase 2 moves it to SILO with `forecast.R`.
- **`src/ABC/`** and **`src/convolutions/`** — model-fitting code. `src/ABC/` is the Kimberley calibration: `kimberley-setup.R` (SILO two-kernel setup, real 2010–2023 extreme-year sequence) → `spread_Kimberley_ABC.R` (resumable parallel batches; scores via `abc-score.R`) → `spread_Kimberley_ABC_concat.R` (top 5% → `dat/Posteriors_<date>.RData`). **Every live application loads the calibration through `load_posteriors()`, i.e. `POSTERIORS_FILE` in `pprocess_functions.R`; change that one line when the calibration is refitted.** `src/convolutions/` holds and the telemetry-resampling procedure (correlated random walk, `cor_angle()`/`nday()`) used to fit dispersal kernel parameters and truncation distances (see `ms/change_log.Rmd` for the rationale). Neither is part of the regular run pipeline: rerun them only to refit the calibration or the kernel table (`dat/Kernel-fits_truncated.RData`, 1–365 movement days, refitted 2026-11-27; the 250-day original is in git history).
- **`src/cluster/`** — HPC environment setup for running large simulations off a local machine.

### Manuscript

`ms/tcz-optimisation-methods.qmd` is the methods writeup (Quarto → PDF) referencing the paper's three arrival-time estimation methods (see `Readme.md`); `ms/change_log.Rmd` documents the historical evolution of the model since the original Tingley et al. code (kernel truncation switch, VRD→Kimberley refit, code restructuring into `setup()`/`spread.pilb()`).

## Data conventions worth knowing

- Coordinates are carried in **Australian Albers (EPSG:3577)** internally (metric, needed for distance-based kernel calculations); raw spatial layers are loaded in WGS84 (EPSG:4326) or their native CRS and reprojected.
- `present.id`/`colonised` columns use `0` = uncolonised, `1` = already colonised, `2` = target site (converted to `0` internally by `setup()`, tracked separately via the `target` column).
- `artificial.natural.id` must be a 0/1 column with **`1` = artificial, `0` = natural**: `setup()` sets `nats = (column == 0)`, and `TCZ = TRUE` drops rows with `TCZ == 1 & column == 0`. The flag only matters when the control step is on (natural points get the drying test, tanks/fences can't sit on natural points), so `forecast.R` passing the character `origin_des` is harmless. `tcz-sims.R` builds `art_nat = !natural` for this; an earlier version passed `origin_des == "Natural"` (inverted) with `TCZ = TRUE`, which removed every TCZ artificial point instead of controlling it. Check the encoding before reusing a script as a template.
- `dat/` and `out/` are gitignored (data and generated outputs respectively); everything under them is either fetched from `DATA_PATH`/external APIs or regenerated by the scripts above.
